# ALE WebUI v5.3 专业评审与优化指南

> 评审日期：2026-09-12  
> 评审对象：[ALE WebUI 仓库](https://github.com/apllozhang/webui)、`ALE-WEBUI-设计规范-v5.3.md`、规范演示站 `http://10.20.30.203:8091/`，并参考 [ale-dan-cpl-system](https://github.com/apllozhang/ale-dan-cpl-system)、[nvci-lite](https://github.com/apllozhang/nvci-lite)、[TSSKB](https://github.com/apllozhang/TSSKB)。  
> 评审性质：设计体系与实际渲染的严格审查；本轮不改业务代码、不做数据库操作。

## 1. 结论先行

ALE WebUI v5.3 已经不是“配色说明”，而是一套有品牌依据、设计令牌、组件规则、工程骨架和验收意识的设计体系。其优势是方向正确、ALE 识别明确、内容型与工具型界面都已有落地参照；但目前仍更接近一份“优秀的内部设计指导”，还没有达到可长期治理、可自动验收、跨框架结果稳定的“企业级 Design System（设计系统）”。

**综合评分：78/100，评级 B+。**

| 维度 | 得分 | 评价 |
|---|---:|---|
| 品牌一致性 | 90 | Logo、品牌紫、法律声明、克制原则清楚 |
| 视觉语言 | 82 | 清晰可信，但卡片化密度偏高，规范页自身略显“组件展板化” |
| 信息架构 | 76 | 内容完整，但分类轴混用，30 章正文不利于日常查找 |
| 组件完备度 | 78 | 核心组件和表格功能较强，复杂应用组件覆盖仍不足 |
| 响应式 | 68 | 375px 以上基本稳定，320px 实测未通过自身验收线 |
| 无障碍 | 70 | 规则意识好，但演示中触控尺寸和标题语义未闭环 |
| 工程落地 | 84 | shared 单一来源与三档骨架是正确方向 |
| 治理与可验证性 | 72 | 有验收清单，但缺机器可读契约、变更流程和差异追踪 |

一句话判断：**保留视觉方向，重构规范的分类方式和验收机制；先解决“文档、令牌、演示、骨架四者不一致”，再扩展组件。**

## 2. 第一印象与产品气质

演示站首屏传达的是“理性、可信、ALE 品牌明确的企业工具规范”。视线顺序是：品牌紫 Hero 标题 → 右侧 ALE Logo → 两个主入口按钮 → 下方七个导航卡片。品牌识别成功，第一屏目标也基本清楚。

![首屏桌面证据](review-artifacts/01-first-impression.png)

我注意到首屏同时使用了 Hero、数据指标、七张导航卡和下一节四张说明卡。单个模块都整洁，但连续卡片会削弱“开放、轻盈”的主张。作为规范站，卡片可以承担导航；作为 ALE 通用范式，不应让下游误读为“所有信息都要装进卡片”。

**设计分类：Hybrid。** Hero 属于品牌/内容页规则，组件、表格和验收区域属于应用界面规则。

### 七项快速判定

| 检查项 | 结果 | 说明 |
|---|---|---|
| 首屏能识别品牌与产品吗 | 是 | ALE Logo 与 WebUI 设计规范清楚 |
| 是否有一个强视觉锚点 | 是 | 紫色 Hero + 大标题 |
| 只扫标题能理解页面吗 | 基本可以 | 章节命名清楚，但规范结构较长 |
| 每个区块是否只有一个任务 | 基本是 | 首屏导航区略拥挤 |
| 卡片是否都有必要 | 否 | “设计气质”和“验收清单”中的部分卡片可改为开放式分组 |
| 动效是否帮助表达状态 | 部分 | 按钮/卡片语言明确，但尚无完整自动验证证据 |
| 去掉阴影仍显高级吗 | 是 | 品牌色、排版和留白仍能维持识别 |

## 3. 必须优先修正的问题

### P0-1：版本真源已经漂移

**我注意到：** 仓库主文档声明 v5.3，但部署站 `<title>`、description 和可见标题仍为 `v5.1`；仓库 README 又把 `spec-site` 描述为“v5.2 的自举实现”。用户无法判断当前看到的是哪一版。

**风险：** 团队会基于旧页面验收新规范，截图、代码引用和缺陷单失去版本可信度。

**修正：**

1. 建立单一版本文件，例如 `design-system.version.json`。
2. 文档页眉、HTML title、页脚、Kit 站和构建产物全部从该文件生成。
3. 页面提供“规范版本、Kit 版本、构建提交 SHA、发布日期”。
4. CI 检查所有入口的版本号一致，不一致则禁止发布。

**验收：** 页面可见版本、HTML 元数据、Markdown 版本、npm/package 版本和部署健康接口返回值完全一致。

### P0-2：320px 响应式承诺未通过

规范第 9、22、28、29 章均要求 320px 无页面级横向滚动。实测：

| 视口 | 页面 scrollWidth | 结果 |
|---:|---:|---|
| 320px | 330px | 失败，页面级溢出 10px |
| 375px | 375px | 通过 |
| 768px | 768px | 通过 |
| 1024px | 1024px | 通过 |
| 1440px | 1440px | 通过 |

表格自身约 954px 宽是允许的，但必须完全限制在横向滚动容器内，不能把宽度传递给页面根节点。

**修正：** 对表格外层明确 `max-width: 100%`、`min-width: 0`、`overflow-x: auto`；逐层检查 Grid/Flex 子项是否遗漏 `min-width: 0`；在 320px 下检查 body 默认边距、卡片阴影和绝对定位元素。

**验收：** `document.documentElement.scrollWidth === document.documentElement.clientWidth`，且表格内部仍可横向滚动、首末列可达、键盘焦点不会被裁切。

### P0-3：44px 触控基线与演示实现矛盾

桌面实测约 42 个、375/768px 实测约 43 个可交互元素的边界小于 44px。包括 40×40 顶栏图标按钮、36px 按钮、32px 分页按钮、22px 排序按钮、16px 复选框。规范正文写“触控目标 ≥44×44px”，附录 F9 又出现桌面 40px 例外，形成两套口径。

这里要区分“可见控件尺寸”和“可点击热区”：复选框图形可为 16px，但其 label/点击热区仍必须至少 44px。

![组件尺寸证据](review-artifacts/03-components.png)

![表格密集控件证据](review-artifacts/04-table.png)

**修正：**

- 规范统一为：触控/粗指针环境热区 ≥44px；桌面精确指针环境可见高度可为 32/36/40px，但焦点与点击热区不得小于 40px，并必须用媒体查询或 density 模式显式切换。
- 增加 `--control-height-compact: 36px`、`--control-height-default: 44px`、`--hit-target-min: 44px`。
- 排序图标、复选框和分页按钮通过伪元素、label 或容器扩大热区，而不是放大图形本身。
- 不再把例外藏在附录；正文必须定义例外条件。

### P0-4：文档规定与演示排版不一致

规范表格规定桌面 h1 为 32px、h3 为 19px；演示实测首屏 h1 为 44px，多组卡片 h3 为约 15.2–15.68px。页面标题从 h1 直接进入多组 h3 后才出现 h2，语义层级不连续。

这不是单纯“字号错了”：Hero Display、页面 h1、卡片标题本来就是三个不同角色，却被当前规范混在 h1/h3 HTML 标签规则里。

**修正：** 建立“视觉角色”和“HTML 语义”两层：

| 视觉角色 | 建议桌面/移动 | 用途 |
|---|---|---|
| Display | 44/32 | 品牌 Hero，可由 h1 承载 |
| Page title | 32/26 | 应用页标题 |
| Section title | 24/21 | 一级内容区 |
| Subsection title | 19/18 | 二级内容区 |
| Card title | 16/16 | 卡片内部，不强制使用 h3 |

HTML 标题仍必须按 h1 → h2 → h3 连续；视觉角色通过 class/token 指定，不用标签本身决定全部外观。

## 4. 信息架构的核心重构建议

用户的真实需求是两类产品：

1. **工具应用型**：复杂工作台与轻量工具。
2. **内容网站型**：静态门户、知识库、产品信息站。

现规范又定义 A 内容、B 应用、C 向导三种“产品形态”。这两个分类不是互斥关系：复杂/轻量描述技术和业务规模，内容/工作台/向导描述交互形态。把它们放在同一层会造成选型困惑。

建议改成二维模型：

| 第一维：产品家族 | 第二维：交互模式 | 推荐工程档 |
|---|---|---|
| 内容网站 | 阅读门户、检索目录、长文详情 | Static |
| 工具应用 | 工作台/数据管理 | React |
| 工具应用 | 单任务/轻量表单 | Alpine 或 Vanilla |
| 工具应用 | 多步向导 | React 或 Alpine，按复杂度选择 |

因此“向导”不应与“应用”并列成第三种产品家族，而应成为工具应用中的一种页面模式。这样才能稳定回答新项目最关心的两个问题：“我属于哪一类产品？”以及“我该选哪套工程骨架？”

## 5. v5.3 文档结构建议

当前 30 章正文内容丰富，但查一个具体答案成本偏高。建议 v6.0 拆成四层，不删除现有内容：

```text
00-foundations/      品牌、色彩、字体、间距、圆角、动效
10-patterns/         内容门户、数据工作台、向导、登录、空/错/加载
20-components/       Button、Input、Table、Dialog、Navigation...
30-governance/       版本、偏离流程、验收、迁移、发布
```

每个组件页统一使用同一模板：

- 何时使用 / 何时不用
- Anatomy（组成）
- 尺寸与令牌
- 默认、hover、focus、active、disabled、loading
- 内容规则
- 响应式规则
- 键盘和读屏行为
- 正确/错误示例
- React、Alpine、Static 对应实现
- 自动化验收 ID

## 6. 设计令牌优化

### 6.1 修正命名层级

当前文本同时出现 `color-action-primary` 和 CSS 中的 `--color-action`。建议正式固定为三层：

```css
/* Primitive：不可直接用于组件 */
--ale-purple-600: #6b489d;

/* Semantic：表达设计意图 */
--color-action-primary: var(--ale-purple-600);
--color-text-heading: var(--ale-purple-700);

/* Component：只在组件需要独立控制时设置 */
--button-primary-bg: var(--color-action-primary);
```

并在 Stylelint/自定义脚本中禁止组件直接引用 primitive。

### 6.2 增加缺失令牌

- 排版：font-size、line-height、font-weight、letter-spacing、measure。
- 控件：compact/default/comfortable 高度与 hit target。
- 布局：sidebar width、header height、content max、reading max。
- 数据密度：row compact/default/comfortable。
- 焦点：focus ring width、offset、color。
- 图标：16/20/24 与 stroke width。

### 6.3 字体策略更严谨

自托管 Noto Sans SC 是正确方向，但每字重约 1.1MB、三字重约 3.3MB，对静态知识站首屏偏重。建议使用 `unicode-range` 分包或可变字体子集，并对中文正文与西文数字做真实平台回归。实测页面计算字体集合中仍出现 Times New Roman 与 Arial，说明至少存在未继承或浏览器默认样式，需定位并消除非预期回退。

## 7. 组件覆盖缺口

现有按钮、状态、表单、Modal、Toast、卡片和表格足以覆盖演示，但复杂 B/S 应用还需要优先补齐：

- App Shell：侧栏、顶部工具区、面包屑、页面头。
- Select/Combobox、Date Picker、Tabs、Menu、Popover、Tooltip。
- Drawer、Command/Search、File Upload、Progress。
- Tree、Empty State、Skeleton、Error Summary。
- 权限只读态、批处理进度、长任务与断线恢复。
- 图表的 tooltip、legend、键盘访问和数据表替代视图。

不要一开始追求组件数量。先完成 App Shell、Form、Table、Feedback 四条高频链路，因为它们决定 ale-dan-cpl-system 和 nvci-lite 的实际效率。

## 8. 视觉提升建议

### 工具应用型

- 减少大面积卡片套卡片，使用“页面结构 + 分隔线 + 局部表面层级”。
- 默认密度保持冷静；只有表格/列表提供 compact 模式。
- 主动作跟随当前任务，不固定把紫色按钮塞进每个区块。
- 数据表格应优先保证扫描、对齐和批量操作，弱化装饰阴影。

### 内容网站型

- 保留 TSSKB 的浅画布、深紫标题和细分隔线。
- 阅读正文最大宽度单独设为约 720–800px，不沿用应用区 1180px。
- 首页可有品牌 Hero，但详情页回归内容优先。
- 相关内容用开放列表或轻分组，避免整站卡片化。

### 演示站自身

验收区目前把五类清单分别放入卡片，视觉整齐但信息密度低，且容易让下游模仿“卡片即分组”。建议改为两栏 checklist 或开放式章节，仅让需要独立交互/选择的对象使用卡片。

## 9. 治理与验收方法

### 9.1 四个真源必须闭环

```text
规范 Markdown
      ↓ 生成/校验
Design Tokens JSON → shared CSS → React / Alpine / Static
      ↓                              ↓
组件契约与测试                    实际演示站
      └──────── 视觉与无障碍回归 ────────┘
```

### 9.2 每次发布的自动门禁

1. 版本一致性：文档、页面、包、部署版本相同。
2. Token lint：禁止硬编码品牌色、间距和 z-index。
3. Axe/ARIA：严重无障碍错误为零。
4. 响应式：320、375、768、1024、1440 五档截图回归。
5. 页面宽度：根节点无横向溢出；局部表格允许容器内滚动。
6. 触控：粗指针模式 44px 热区覆盖率 100%。
7. 对比度：亮/暗主题令牌组合自动计算。
8. 键盘路径：菜单、Dialog、表格排序、列宽、分页、表单可完成。
9. 动效：`prefers-reduced-motion` 下无非必要位移动画。
10. 三类样板页：内容门户、数据工作台、多步向导各至少一页通过。

### 9.3 偏离流程

增加 `design-exceptions.yml`，每个偏离必须写：条款 ID、项目、原因、负责人、影响、替代措施、复审日期。没有到期复审日期的例外不得合并。

## 10. 分阶段实施路线

### 第一阶段：一致性止血，1–2 周

- 修正 v5.1/v5.2/v5.3 版本漂移。
- 修复 320px 根级溢出。
- 统一 44px 热区与桌面 compact 例外。
- 分离 Display/Page title/Card title 与 HTML 标题语义。
- 统一 `color-action-primary` 命名。

**完成定义：** 演示站能真实通过自己写出的强制条款。

### 第二阶段：体系重构，2–4 周

- 把两类产品家族与三种交互模式改为二维模型。
- 将长规范拆分为 foundations/patterns/components/governance。
- 建立组件文档模板、设计例外流程和令牌 Schema。
- 补 App Shell、表单、表格、反馈四条核心链路。

### 第三阶段：工程门禁，2–3 周

- 建立截图回归、axe、对比度、断点和版本一致性检查。
- 三骨架同时跑契约测试，不允许各自漂移。
- 每次版本抽查 TSSKB、ale-dan-cpl-system、nvci-lite 的真实页面。

### 第四阶段：迁移与推广，持续

- 为旧项目提供 v5.x → v6 token 对照表和 codemod/检查脚本。
- 发布“正确/错误示例库”和常见页面模板。
- 每季度收集真实项目例外，只有重复出现的例外才升级为正式模式。

## 11. 30 分钟内可完成的 Quick Wins

1. 把演示站页面 title、description、页脚版本统一到 v5.3。
2. 在首屏明确标注“产品家族 2 类 / 交互模式 3 种”，避免概念冲突。
3. 给表格外层补 `min-width: 0; max-width: 100%` 并验证 320px。
4. 将所有分页按钮和顶栏图标按钮的点击热区扩至 44px。
5. 把验收区的装饰卡片改为开放式两栏清单，示范“卡片需要理由”。

## 12. 最终建议

不建议继续以 v5.4 的方式在同一篇长文末尾叠加更多规则。下一步应定为 **v6.0 治理版**：视觉风格基本不变，重点重构分类、令牌契约、组件文档和自动验收。

ALE WebUI 最有价值的差异化，不是“紫色企业界面”，而是：**ALE 品牌的可信感 + 内容门户的清爽阅读 + 网络工具的高密度效率 + 可被工程自动验证的一致性。** 围绕这四点收敛，才能让 TSSKB、复杂业务系统和轻量向导看起来属于同一个品牌，同时又不被迫长成同一个页面。
