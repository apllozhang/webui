## 1. 一页摘要

我们为 ALE 品牌下的 B/S 系统（门户、知识库、业务系统、工作台）建立了一套**可执行、可验证、可交付**的 WebUI 设计体系，包含四层交付物：

```
设计规范（文档，多章 + 附录 A–H，当前最新版）
   ↓ 自举实现
规范演示站（当前版规范的自举实现，线上可交互）
   ↓ 工程化
ale-webui-kit 工程骨架（复杂 React 档 / 轻量 Alpine 档 / 静态 Jinja2 档，共享令牌单一来源）
   ↓ 交付
Docker 化部署基线（nginx + 协商缓存 + 健康检查，两套在线站点）
```

**三个最有把握的成果**：①品牌事实全部对回 ALE 官方品牌指南（September 2025）；②全部文字/图形令牌完成 WCAG 对比度实测并修正了一处不达标值（附录 G）；③规范不是纸面文档——它被自己的演示站和三个骨架完整实现过，踩过的坑都写进了规范附录 F。

> **v5.3 增补（2026-09-12）**：吸收 Material Design 3 机制层——3.3A 前景色角色（on-*）、11.1 状态层（on-* 色 × 8%/10%/12% 固定透明度）、`--ease-emphasized` 正名、附录 H 提供 Ant Design 5 下游映射表；中文字体替换为**自托管 Noto Sans SC**（思源黑体，OFL 1.1 免费商用），字体栈移除商业授权字体声明。设计语言底座维持自研，M3 仅吸收机制不引入风格。

**最希望获得专家指点的**：第 9 节列出的 10 个开放问题（品牌字体、深色主题合法性、4px 栅格、图标按钮尺寸等）。

## 2. 背景与问题定义

ALE 内部存在三类 Web 系统，此前各自为政、视觉漂移严重：

| 类型 | 现状参照 | 痛点 |
|---|---|---|
| 复杂工具应用 | ale-dan-cpl-system（报价管理：登录、数据表格、导入导出） | 表格能力靠手写 hook，无障碍缺失，主题/多语言各搞一套 |
| 轻量工具应用 | nvci-lite（四步向导工作台） | 内联样式、无令牌、与复杂档视觉不一致 |
| 静态内容站 | TSSKB（培训知识库门户） | 视觉最佳但未沉淀为可复用规范 |

**问题定义**：如何在"官方品牌指南 + WCAG 2.2 AA + 三类异构系统"约束下，建立一套设计语言，使得新项目开箱即符合品牌与无障碍要求，且跨系统视觉一致。

## 3. 设计理念

### 3.1 五个气质关键词

清晰、可信、开放、高效、有辨识度——其中"辨识度"被明确约束为：**Logo 与命名正确 > 信息结构清晰 > 紫色用于关键动作 > 细节装饰**。紫色（Pantone 267C / `#6B489D`）占比严格控制在 10–15%，绝不整页渲染品牌色。

### 3.2 清爽感的四个来源（从 TSSKB 实测归纳）

1. 大面积中性底（画布 `#F7F7F5` + 白表面），品牌紫只出现在关键动作与强调位；
2. **标题用深紫 `#4F3478` 而非纯黑**，正文近黑 `#1A1A1A`——品牌感来自文字色而非色块；
3. 两档浅色分隔：主边框 `#D9D9D6` + 次级柔和线 `#E9E8E4`（虚线），避免满屏等重边框；
4. 紫灰基调阴影（`rgb(32 25 46 / …)`，非纯黑）+ 轻浮起（-2px 级）。

### 3.3 证据分层（规范的宪法）

规则按证据强度分级：**L1 官方品牌规则**（Logo/色彩/字体/法律，不可违背）→ **L2 本规范 Web 规则**（令牌/无障碍/组件状态，必须或建议）→ **L3 项目级主题**（在不破坏前两层下扩展）。任何冲突按此顺序裁决；参考实现（TSSKB 等）永远不是规范本身。

## 4. 方法论：六步闭环

```
① 品牌溯源   官方 Brand Guidelines（Sept 2025）→ Pantone 267C、五档色板、Logo 净空、法律文本
② 实测归纳   拆解 TSSKB 四份 CSS 原件 → 提炼令牌/动效/布局的真实可用值
③ 令牌化     三层令牌（Primitive → Semantic → Component），语义层承载亮/暗主题
④ 组件化     六态控件（默认/悬停/焦点/按下/禁用/加载）+ 14A 表格功能包
⑤ 工程化     ale-webui-kit 三档骨架，令牌单一来源 + sync-shared 同步机制
⑥ 验证闭环   线上部署 + 浏览器实测 + 量化自查（附录 G）+ 踩坑回流规范（附录 F）
```

关键机制：**踩坑回流**。实现与部署中发生的每一个问题（F1–F9）都转化为规范的可执行条款，而不是停留在口头经验——这是 v5.2 与 v5.1 最大的差异。

## 5. 业界对标：我们参考了什么

| 业界体系 | 采纳/借鉴的点 | 我们的落地 |
|---|---|---|
| **IBM Carbon Design System** | 分层 design tokens（primitive/semantic/component）、4px 栅格、无障碍量化检查表 | 三层令牌命名法；4px 间距网格；附录 G 对比度全量实测 |
| **Material Design 3** | 语义色承载主题（动态取色思想）、动效时长 token 化 | 亮/暗主题仅映射语义层；`--motion-fast/panel/enter` 四档时长 |
| **Microsoft Fluent 2** | 深色主题不做简单反色、按表面层级定义背景 | 暗色画布/表面/边框三档独立取值（`#171420/#211D2C/#3D3750`） |
| **Atlassian Design System** | 状态色与品牌色严格分离、组件"意图"API | `tone=neutral|info|success|warning|danger`；禁止 `purple=true` 式参数 |
| **Ant Design / Arco** | 企业级表格交互完整度基准（排序/列宽/批量/分页是标配不是增强） | 14A 数据表格功能包（8 项能力定为形态 B 标配） |
| **shadcn/ui + Radix** | 无障碍原语内置的组件分发模式（源码进项目而非 npm 依赖）、CSS 变量主题 | React 骨架组件按 shadcn 风格手写最小集，preset 与 Radix 变量层兼容 |
| **WCAG 2.2 AA + WAI-ARIA APG** | 对比度 4.5:1、焦点可见、键盘全操作、`aria-sort`/`aria-modal`/live region | 无障碍基线章 + 验收清单；表格排序用 `button + aria-sort`（修正参照仓库的 `th@onclick` 反模式） |
| **Apple HIG / Material** | 触控目标尺寸基准（44pt/48dp） | 触控目标 ≥44px（桌面指针输入图标按钮 40px 例外） |
| **Nielsen Norman Group** | 空状态三问（什么/为什么/下一步）、错误信息公式（发生+影响+行动） | 16.1 空状态表、24 章错误公式 |
| **Tailwind / Open Props** | 工具类与 CSS 变量的混合工程实践 | Tailwind preset 全量映射规范令牌，禁止工具类里写裸色值 |

**刻意的不跟随**：不做品牌级的深色独立品牌（暗色仅是语义令牌映射，保持紫为主色）；不引入远程品牌字体文件（Trebuchet 系统栈，官方指南要求）；不为静态站上 SPA 框架。

## 6. 技术选型与理由

| 档位 | 选型 | 为什么 |
|---|---|---|
| 复杂应用 | Vite + React 18 + TS + Tailwind + **TanStack Table** + shadcn 风格组件 + i18next | 参照仓库已验证；TanStack 无头表格替代手写 hook（排序/列宽拖动/虚拟化成熟且无障碍友好）；Radix 语义使键盘/读屏达标成本最低 |
| 轻量应用 | vanilla + **Alpine.js**（本地 vendored 55KB，内网无 CDN 依赖） | 不引入构建链；明确的升级阈值（需要完整 14A 或登录态 → 迁 React 档） |
| 静态站 | Python/Jinja2 + **Pagefind** | 内容供应链（校验/断链/发布）在 Python 侧是资产；Pagefind 是静态站搜索成熟方案（构建时索引、零后端、中英分词） |
| 交付 | nginx:alpine + Docker，CSS/JS 协商缓存，相对路径构建 | 子路径可移植；杜绝无哈希文件的强缓存事故 |

## 8. 关键设计决策与量化依据

| 决策 | 依据 |
|---|---|
| 白字压在主紫 `#6B489D` 上做 Primary 按钮 | 对比度 6.91:1，超过 AA 正文要求（附录 G） |
| 辅助文字 `#616467`（v5.2 修正） | 原 `#75787B` 实测 4.44:1 不达 AA；修正后 5.95:1 |
| 微交互 160ms / 面板 240ms / 入场 560ms（一次性） | TSSKB 全站实测 0.16s ease；对齐 Material/Carbon 动效 token 量级；入场仅首屏一次防炫技 |
| 按钮 hover `translateY(-2px)` + 按下归零 | 全站统一的"浮起-按压"语言；只动画 transform/box-shadow，不触发重排 |
| 内容宽 1180px | TSSKB 实测值，处于 Carbon(1152) 与常见 1200 容器之间；长文行宽 60–80 汉字 |
| 状态"圆点+文字"双表达 | 颜色不单独传达状态（WCAG 1.4.1）；官方亮色只用于图形（圆点/图标），文字恒用深色派生值 |
| 4px 栅格（非 8px） | 表单/表格等高密度企业场景需要 4/12/20 等中间档；Carbon 亦为 4px 基础网格 |

## 9. 开放问题（恳请专家重点评审）

1. **品牌字体**：官方指南指定 Trebuchet MS，视觉年代感明显且无官方 Web Font。我们遵守了品牌规则，但是否存在"用现代可变字体做数字端替代"的品牌合规路径？（如 Inter/Noto Sans 配 Trebuchet 回退）
2. **深色主题的品牌合法性**：ALE 官方无深色色板。我们的暗色令牌是从品牌色板体系推导的（对比度全部实测达标），但**是否应该允许暗色主题出现在对外品牌站点**？目前规范将其标为"可选，对外站可禁用"。
3. **4px vs 8px 栅格**：企业密集型界面我们选了 4px 基础网格。是否会造成设计/实现协作中的间距噪声？是否应收敛为 8px 主档 + 4px 半档？
4. **图标按钮 40px 例外**：顶栏图标按钮 40×40px 低于 44px 触控标准（我们的豁免仅限桌面指针输入）。专家是否认可此例外，还是应统一 44？
5. **14A 功能包的边界**：我们把排序/列宽拖动/换行/分页/防抖搜索/批量/主题/多语言定为复杂应用"标配"。这是否过重？小型内部工具是否应强制降级？
6. **紫色占比 10–15% 的度量**：目前靠评审目测。是否值得定义可计算的度量（如首屏像素采样）？
7. **标题深紫 vs 纯黑**：深紫标题是"清爽+品牌感"的关键来源，但在数据密集表格内嵌标题时是否应回退中性色（我们目前的规则是标题色仅用于区块级）？
8. **状态语义五档是否够用**：现有 neutral/info/success/warning/danger。业务上出现过"已暂停/部分成功"等中间态，是并入现有五档还是扩展？
9. **多语言基线**：规范要求六语言（zh/zh-TW/en/ja/es/fr），演示站只实现了 zh/en。六语言是否应作为强制验收项，还是按项目市场裁剪？
10. **阴影三档 vs 扁平化趋势**：我们保留了轻阴影+浮起动效（TSSKB 风格）。若专家认为应更扁平（仅边框分隔），动效语言需要相应调整。

## 10. 建议的评审方式

1. **先读**：规范 v5.3 第 1–3 章（理念与令牌）→ 11.1 状态层 → 3.3A 前景色角色 → 附录 F（踩坑）→ 附录 G（量化数据）→ 附录 H（Ant Design 映射）；
2. **再操作**：:8091 演示站实际点击（亮暗切换、表格排序/列宽拖动/键盘 ←→、批量删除、模态、Toast、中英切换）；:8095 三个骨架对比同一套令牌的三种工程形态；
3. **后批注**：直接在 GitHub 上对规范当前版逐条 comment，或在 Issues 中按"章节-条款"编号提出；开放问题（第 9 节）建议逐项给出倾向性意见。

**我们对评审的承诺**：所有意见将在 v5.4 中逐条回应（采纳/部分采纳/不采纳+理由），并保持踩坑回流机制——专家在评审中发现的问题也会进入附录 F 的循环。
